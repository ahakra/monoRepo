# Configuration

Start PostgreSQL from the repository root:

```sh
docker compose --env-file .env -f docker/compose.postgres.yml up -d
```

Create `.env` from `.env.example` first if needed (`cp .env.example .env` from the repository root). Compose requires nonempty `POSTGRES_DB`, `POSTGRES_USER`, and `POSTGRES_PASSWORD`. Camel reads the same root `.env` when launched from the repository root or this service directory; environment variables can override those values. The default JDBC URL uses `localhost:5432` and `POSTGRES_DB`. Set `POSTGRES_JDBC_URL` for another database host or port.

If Java fails while initializing Flyway, check `docker compose --env-file .env -f docker/compose.postgres.yml ps` and container logs from the repository root. A restarting container with “superuser password is not specified” means Compose was started without the settings. Rerun the command above with `--env-file .env`; the existing data volume is preserved. If port 8081 is occupied, check whether an IDE instance is already serving the API before starting a second instance.

Run `./mvnw spring-boot:run` in this directory, and `npm run dev` in `apps/workflow-designer`. Open **Connectors** in the sidebar. The Vite development server proxies `/api` to Camel on port 8081. Production hosting must also proxy `/api` to Camel.

Flyway creates `etl_connections` and `etl_connection_settings`; JPA maps these tables and validates their schema. Existing `integration_connections` rows are migrated once; the legacy table is retained as a backup. Saved configurations survive restarts through the existing Docker volume. The target connection host is resolved from the Camel process: use `localhost` when running Camel on the host, or `postgres` on the same Docker network.

API:

- `GET /api/connections`: list configurations, excluding passwords.
- `POST /api/connections`: create a configuration.
- `PUT /api/connections/{id}`: update; blank or omitted password preserves the saved password.
- `DELETE /api/connections/{id}`: delete a configuration.
- `POST /api/connections/test`: test unsaved fields.
- `POST /api/connections/{id}/test`: test edited fields, reusing the saved password when blank.

Create, update, and test accept `name`, `type`, `password`, and a type-specific `settings` map. For example:

```json
{
  "name": "Analytics destination",
  "type": "postgres",
  "password": "your-password",
  "settings": {
    "host": "localhost",
    "port": "5432",
    "database": "analytics",
    "username": "camel_etl",
    "sslMode": "disable",
    "createDatabaseIfNotExists": "true"
  }
}
```

Settings values are strings. PostgreSQL supports SSL modes `disable`, `require`, and `verify-full`. Saving only persists configuration. With `createDatabaseIfNotExists` enabled, **Create & test** first tries the target database. Only a missing-database error triggers creation through the `postgres` maintenance database, followed by another connection test. Existing databases do not require creation privileges. The account must have `CREATEDB` to create a missing database; creation runs outside a transaction as required by [PostgreSQL](https://www.postgresql.org/docs/current/sql-createdatabase.html). Turning the option off never creates a database. Configurations are not yet attached to pipeline execution.

The Java packages separate responsibilities:

- `api`: HTTP controller, request/response DTOs, error mapping.
- `application`: framework-independent connection use cases and commands.
- `domain`: connection model, persistence port, and connection type handler contract.
- `infrastructure/persistence`: JPA entity, Spring Data repository, and persistence adapter.
- `infrastructure/postgres`: PostgreSQL validation, JDBC connection factory, and connection testing/creation.

To add another type, register a `ConnectionTypeHandler` bean with its own settings validation and testing behavior, and add its frontend form. The application service dispatches by type; the entity and repository have no database-specific fields. File is also implemented; MySQL and HTTP remain extension points.

## Fields

Open **Schemas & Tables → Fields** to create, edit, or delete named, reusable field dictionaries. Each definition includes the default entries `id: uuid` and `datetime: datetime`; their keys and types are fixed. Add custom entries such as `name: string` and `lastname: string`.

The field dictionary describes future data columns. Separately, each saved definition has its own UUID `id`, `createdAt`, and `updatedAt` metadata, generated by the service. Saving a definition creates no external table and needs no connection.

- `GET /api/fields`: list saved definitions, most recently updated first.
- `POST /api/fields`: create a definition; returns the saved definition with HTTP 201.
- `PUT /api/fields/{id}`: replace the name and dictionary; returns the saved definition, preserving its ID and creation time.
- `DELETE /api/fields/{id}`: delete a definition and its entries; returns HTTP 204.

Create and update accept:

```json
{
  "name": "Customer",
  "fields": {
    "id": "uuid",
    "datetime": "datetime",
    "name": "string",
    "lastname": "string"
  }
}
```

Default entries are added when omitted, and conflicting types are rejected. Supported types are `string`, `integer`, `long`, `decimal`, `boolean`, `date`, `datetime`, `uuid`, and `json`. Keys must match `[a-z_][a-z0-9_]{0,62}`. Names contain 1–120 characters; definitions contain at most 100 entries including defaults. The editor rejects duplicate keys before saving. Invalid definitions return HTTP 400 with a problem detail; missing definitions return HTTP 404.

Flyway migration V3 adds `etl_field_definitions` and `etl_field_entries` to internal platform persistence. The `fields` Java package follows the same API/application/domain/infrastructure separation as connections. Migration V4 seeds **CDR (Call Detail Record)** once, with `id`, `datetime`, `call_id`, `caller_number`, `called_number`, `start_time`, `end_time`, `duration_seconds`, `direction`, `call_status`, `charge_amount`, and `currency`. This sample contains only field definitions, not call records. It can be edited or deleted like other definitions, and deleting it does not cause it to be reseeded on restart.

## Tables

Open **Schemas & Tables → Tables**, choose an existing PostgreSQL connection and one Fields definition, and provide a configuration name, existing schema (default `public`), and table name. **Add all fields** selects the entire dictionary; **Add one field** adds only the chosen key. Fields can be removed from the selection, including `id` and `datetime`. At least one field is required. Keys and types cannot be entered independently of the selected dictionary. Changing the Fields definition clears the selection.

Saving stores configuration only. From the saved list, inspect **View CREATE TABLE SQL**, then use **Create PostgreSQL table** to review the target and execute creation. This uses the saved connection credentials without returning them to the browser. It does not create a database or schema. An existing target relation returns a conflict rather than being modified. Editing or deleting a saved configuration never alters or drops an external table, and a successful creation message does not track future changes to that table.

- `GET /api/tables`: list configurations, including selected `columns` as a key/type dictionary and generated `sql`.
- `POST /api/tables`: save a configuration; returns the saved configuration with HTTP 201.
- `PUT /api/tables/{id}`: replace a configuration; returns the saved configuration.
- `DELETE /api/tables/{id}`: remove configuration only, with HTTP 204.
- `POST /api/tables/{id}/create`: explicitly create the physical PostgreSQL table; returns a success message.
- `GET /api/tables/{id}/schema-plan`: compare the current PostgreSQL columns with the saved mapping; returns a review fingerprint and proposed changes.
- `POST /api/tables/{id}/schema-changes`: apply selected changes from a current review.

Create and update accept:

```json
{
  "name": "CDR destination",
  "connectionId": "<saved-postgres-connection-uuid>",
  "fieldDefinitionId": "cd000000-0000-4000-8000-000000000001",
  "schemaName": "public",
  "tableName": "cdr_records",
  "fields": ["id", "datetime", "caller_number", "called_number", "duration_seconds"]
}
```

The API independently enforces PostgreSQL connection type, validates selected keys against the saved definition, rejects duplicate or empty selections, and derives column types on the server. It rechecks the connection and selected fields before external creation. Schema, table, and column identifiers follow the same lowercase 63-character rules as field keys, and generated SQL quotes each identifier. Types map as follows:

| Field type | PostgreSQL type |
| --- | --- |
| `string` | `TEXT` |
| `integer` | `INTEGER` |
| `long` | `BIGINT` |
| `decimal` | `NUMERIC` |
| `boolean` | `BOOLEAN` |
| `date` | `DATE` |
| `datetime` | `TIMESTAMP WITH TIME ZONE` |
| `uuid` | `UUID` |
| `json` | `JSONB` |

Columns are nullable, with no automatic primary keys, defaults, or indexes. Creation executes a single constrained `CREATE TABLE` statement. A timeout may leave creation outcome uncertain; check the target database before retrying.

Migration V5 adds `etl_table_definitions` and `etl_table_columns`, with a unique target per saved connection/schema/table. Foreign keys prevent deleting a referenced connection or Fields definition (HTTP 409). The Fields service prevents removing, renaming, or changing the type of a selected field until **every** dependent table configuration releases it. These conflicts return HTTP 409. Field definitions returned by the API include `usedBy` references with table IDs, names, and selected keys/types. The editor locks used keys and types, shows their references, and disables deletion of used definitions. Unselected fields and definition names can still change. Field updates, deletes, and table-mapping saves hold the same definition row lock across usage validation and persistence, preventing concurrent mapping saves from bypassing the check. Table configuration stores a snapshot of selected keys and types.

### Reviewing and applying column changes

To change a field type or key:

1. Remove the column from every affected table mapping and save those mappings.
2. Edit the field in Fields and save.
3. Add the updated field back to the table mapping and save.
4. Use **Review column changes**, select the desired changes, review their SQL, acknowledge any DROP/ALTER data-loss risk, and apply.

To drop a physical column, remove it from the mapping, save, then select the proposed DROP in the review. Saving a mapping alone does not execute column changes. The review also lists actual database columns absent from the mapping, including columns added outside the application; all changes start unselected. Renaming a field produces separate ADD and DROP suggestions and does not copy existing data to the new name.

ADD creates a nullable column using the allowlisted field type. ALTER converts values using an explicit cast to that type, which can lose precision or fail for incompatible data or defaults. DROP permanently removes column values. The service never appends CASCADE. Partitioned/inherited tables and type changes to identity/generated columns require direct PostgreSQL management.

Example apply request:

```json
{
  "fingerprint": "<fingerprint-returned-by-schema-plan>",
  "changeIds": ["alter:duration_seconds", "drop:obsolete_column"],
  "acknowledgeDataLoss": true
}
```

The client submits change IDs, never executable SQL. The server locks the saved mapping and the target PostgreSQL table, reads current column metadata and constraints, rebuilds the plan, and rejects a stale fingerprint or unknown change ID. Only selected changes execute, in one PostgreSQL transaction with lock and statement timeouts. Conversion or dependency failures roll back that transaction. After connection loss near commit, inspect the database and refresh the plan before retrying; the UI requires a fresh review after an apply error. PostgreSQL permissions still determine which operations the saved connection can execute.

Migration and CRUD tests use H2; PostgreSQL JDBC creation, schema planning, selected execution, acknowledgment, stale-plan rejection, and rollback/error handling are tested with mocked connections.

This first iteration is for a trusted local workspace: the API has no authentication and passwords are stored as plaintext in the configuration database, although never returned by the API. Restrict access to the service and database. Add authentication and a secrets store before exposing it to other users.

Run `./mvnw test` for service tests (isolated H2 test database) and `npm run build` / `npm run lint` in the frontend directory.


Formatting is configured at the repository root. Run `npm ci` there once, then `npm run format` to format the Java and frontend sources, or `npm run format:check` to check them. Java uses four-space indentation; JavaScript, JSX, and CSS use two spaces.

## Normalize rules

Migration V6 adds `etl_normalize_rules`. Use the Rules page to configure a name,
optional description, Fields definition, source key, condition/value,
action/value, and destination key. Both keys must belong to the selected
Fields definition and have `string` or `text` type. The current Fields API
exposes `string` as its text type. The service validates selectors and values
independently of the UI, and locks the Fields definition while saving a rule.
Referenced definitions cannot be deleted; referenced keys cannot be removed
or changed to non-text types until the rule is edited or deleted.

Endpoints:

- `GET /api/rules/normalize`: list saved rules (`id`, `spec`, `createdAt`, `updatedAt`).
- `POST /api/rules/normalize`: save a new rule from a spec.
- `PUT /api/rules/normalize/{id}`: update a saved rule from a spec.
- `DELETE /api/rules/normalize/{id}`: delete a saved rule.
- `POST /api/rules/normalize/test`: evaluate an unsaved spec with `{ "spec": {...}, "record": {...} }`.
- `POST /api/rules/normalize/{id}/apply`: evaluate a saved rule against a JSON record supplied directly as the request body.

Example spec:

```json
{
  "name": "Local phone number",
  "description": "Remove the country prefix when present",
  "fieldDefinitionId": "<saved-fields-uuid>",
  "sourceField": "phone",
  "condition": "STARTS_WITH",
  "conditionValue": "+961",
  "action": "REMOVE_PREFIX",
  "actionValue": "+961",
  "destinationField": "normalized_phone"
}
```

Conditions: `STARTS_WITH`, `ENDS_WITH`, `CONTAINS`, `EQUALS`, `LENGTH_EQUALS`,
`LENGTH_GREATER_THAN`, `LENGTH_LESS_THAN`. Length values are strings containing
non-negative integers up to 2147483647; length counts Unicode code points.
Text comparisons are case sensitive. `EQUALS` accepts an empty string.

Actions: `COPY`, `ADD_PREFIX`, `ADD_SUFFIX`, `REMOVE_PREFIX`, `REMOVE_SUFFIX`,
`TRIM`, `UPPERCASE`, `LOWERCASE`, `REPLACE`. Prefix/suffix actions require a nonempty
`actionValue`, preserved exactly (including whitespace). Removal affects only
a matching prefix/suffix once. Case conversion uses `Locale.ROOT`; trim uses
Java `String.strip()`. For `REPLACE`, `actionValue` is the required nonempty find text and `replacementValue` is the replacement string (up to 2000 characters). Replacement is literal and case sensitive, affects every occurrence, and allows an empty replacement to remove text. No regular expressions or replacement escape syntax are used. Migration V7 adds `replacement_value` with an empty default for existing rules. Other actions ignore `replacementValue`; actions without a text argument ignore `actionValue`.

Evaluation returns `{ "matched": true|false, "record": {...} }`. On a match,
the transformed source replaces the destination (which may be the source
itself). On a non-match the record is unchanged, including an existing
destination value. Null, absent, or non-string sources never match. The Java
evaluator copies its input and preserves unrelated fields and null values.
The UI's sample test calls this same Java evaluator. Rules are not yet attached
to the workflow designer or automatic Camel execution.

## Conditional rules

Migration V8 adds `etl_conditional_rules` and `etl_conditional_rule_fields`.
Conditional rules are predicates: evaluation returns `{ "matched": true|false,
"record": {...} }` and never modifies the record. Each rule has a name, optional
description, Fields definition ID, and recursive expression. Groups combine
children with `AND` or `OR`, and may contain comparisons and other groups.
Limits are 8 levels (root counts as one) and 100 total nodes per rule.
Empty groups are rejected.

Endpoints:

- `GET /api/rules/conditional`: list saved rules.
- `POST /api/rules/conditional`: create a rule from a spec.
- `PUT /api/rules/conditional/{id}`: update from a spec.
- `DELETE /api/rules/conditional/{id}`: delete a rule.
- `POST /api/rules/conditional/test`: test `{ "spec": {...}, "record": {...} }`.
- `POST /api/rules/conditional/{id}/apply`: evaluate a saved rule; the request body is the record itself.

Example spec:

```json
{
  "name": "Completed after start",
  "description": "Check chronological order and call status",
  "fieldDefinitionId": "<saved-fields-uuid>",
  "expression": {
    "type": "GROUP",
    "junction": "AND",
    "children": [
      {
        "type": "COMPARISON",
        "field": "end_time",
        "operator": "GREATER_THAN",
        "operandType": "FIELD",
        "otherField": "start_time"
      },
      {
        "type": "GROUP",
        "junction": "OR",
        "children": [
          {
            "type": "COMPARISON",
            "field": "status",
            "operator": "EQUALS",
            "operandType": "VALUE",
            "value": "completed"
          },
          {
            "type": "COMPARISON",
            "field": "duration_seconds",
            "operator": "GREATER_THAN",
            "operandType": "VALUE",
            "value": "60"
          }
        ]
      }
    ]
  }
}
```

All Fields types are selectable. `EQUALS`, `NOT_EQUALS`, `IS_NULL`, and
`IS_NOT_NULL` support every type. Ordered comparisons (`GREATER_THAN`,
`GREATER_OR_EQUAL`, `LESS_THAN`, `LESS_OR_EQUAL`) support numeric, string/text,
date, and datetime fields. `STARTS_WITH`, `ENDS_WITH`, and `CONTAINS` require
string/text fields. A null check omits `operandType`, `value`, and `otherField`.

Field operands must have the same type, except that all numeric types may
compare with each other and string/text are compatible. Numeric values use
`BigDecimal`, with integer/long range checks. Numeric literals may be JSON
numbers or numeric strings; use strings for exact high-precision decimals.
Dates are strict ISO dates (`2026-10-28`); datetimes require an offset or Z
(`2026-10-28T12:00:00Z`) and are compared as instants. Booleans accept true/false
or their lowercase text forms. UUID comparisons validate and normalize UUIDs.
JSON supports structural equality, including numeric equivalence. Text is case
sensitive and ordered by Java string comparison, without locale collation.

Missing/null values only match the explicit null operators. All other
comparisons, including `NOT_EQUALS`, return false when either operand is
missing/null or cannot be converted to the declared type. Bad configured
literals/operators/field selections return HTTP 400, while invalid runtime
data simply does not match. A malformed child is rejected even when another
child would short circuit evaluation.

Saving validates the whole tree and persists a snapshot of all referenced
field types, including right-hand field operands. Fields definitions are locked
through validation and persistence. Referenced definitions cannot be deleted,
and referenced keys cannot be removed or change type until the Conditional
rule releases them. Unreferenced fields remain editable. The field editor
shows these rule references using the existing `usedBy` response structure.

Tests cover nested logic, both operand kinds, dates/timezones, numeric precision,
all field types, null handling, invalid configuration, persistence, API errors,
and field-usage protection. Conditional rules are not yet connected to automatic
workflow/Camel execution.

## Mappers

Migration V9 adds `etl_mappers` and its ordered `etl_mapper_outputs` collection.
Use **Dynamic → Mapper** to configure a name, optional description, WASM directory,
separate WASM filename, and 1–100 typed output lists. This stores configuration
only: it does not read or execute the module and does not check file existence.

Endpoints:

- `GET /api/mappers`: list mapper configurations and saved output schemas.
- `POST /api/mappers`: create a mapper.
- `PUT /api/mappers/{id}`: edit a mapper, replacing its ordered output list configuration.
- `DELETE /api/mappers/{id}`: delete a mapper and its output configurations, leaving files and Fields definitions intact.

Create/update request:

```json
{
  "name": "CDR parser",
  "description": "Parse records into calls and customers",
  "directory": "/opt/etl/mappers",
  "wasmFileName": "cdr_parser.wasm",
  "outputs": [
    {"name": "CallRecords", "fieldDefinitionId": "<calls-fields-uuid>"},
    {"name": "Customers", "fieldDefinitionId": "<customers-fields-uuid>"}
  ]
}
```

Mapper names allow up to 120 characters; descriptions allow 2000. The directory
allows up to 2048 characters. The filename allows 255 characters, requires a
`.wasm` extension, and cannot contain directory separators or control characters.
Both location components are preserved exactly, and directories may contain spaces.

Output list names allow up to 120 characters, must be unique within the mapper,
and cannot contain spaces, whitespace, or control characters. Names are case
sensitive and are never trimmed, lowercased, or otherwise normalized: configure
the exact names the module will emit. There is no runtime module output check yet.
Different outputs may use the same Fields definition. Responses include generated
`id`, `createdAt`, `updatedAt`, and a `fields` map of keys/types for each output.
The client chooses a Fields definition as the entire list item type; it does not
provide arbitrary field snapshots.

All selected Fields definitions are locked in sorted UUID order through schema
validation and persistence. Each output stores its field type snapshot. Referenced
Fields definitions cannot be deleted, and referenced field keys/types cannot be
removed or changed until mapper outputs release them. Fields references appear
in the existing `usedBy` structure, labeled with the mapper and output name.
New keys may be added to Fields; existing snapshots remain stable until the mapper
is saved again. Deleting or changing the output releases its prior definition.

Tests cover multi-output persistence, exact names, order and edit replacement,
shared Fields types, validation/API errors, schema protections, and deletion.

## Dynamic: Transformers

The Dynamic page groups Mapper and Transformer configuration; existing
`#mappers` links still open Dynamic. Mapper API paths and saved data are unchanged.

Migration V10 adds `etl_transformers`, `etl_transformer_inputs`, and
`etl_transformer_outputs`. A transformer has a name, optional description, required WASM directory and
filename, 1–100 inputs, and 1–100 outputs. Every port has an exact name and a kind:

- `FIELD_LIST`: list items use a selected Fields definition; `fieldDefinitionId` is required.
- `DYNAMIC_VARIABLE`: named, untyped placeholder; `fieldDefinitionId` must be null/omitted.

There is no transformer evaluator, expression, runtime value, or execution endpoint
in this iteration. The port name identifies the variable; its evaluation and
runtime typing will be designed later. Variable-only transformers do not depend
on any Fields definitions.

Endpoints:

- `GET /api/transformers`: list saved definitions, including both port schemas.
- `POST /api/transformers`: create a configuration.
- `PUT /api/transformers/{id}`: edit and replace its ordered input/output configuration.
- `DELETE /api/transformers/{id}`: delete the configuration and ports.

Example request:

```json
{
  "name": "Enrich calls",
  "description": "Combine call records with a dynamic threshold",
  "directory": "/opt/etl/transformers",
  "wasmFileName": "enrich_calls.wasm",
  "inputs": [
    {"name": "Calls", "kind": "FIELD_LIST", "fieldDefinitionId": "<saved-fields-uuid>"},
    {"name": "threshold", "kind": "DYNAMIC_VARIABLE"}
  ],
  "outputs": [
    {"name": "EnrichedCalls", "kind": "FIELD_LIST", "fieldDefinitionId": "<saved-fields-uuid>"},
    {"name": "recordCount", "kind": "DYNAMIC_VARIABLE"}
  ]
}
```

Names are case sensitive, preserved without normalization, and cannot contain
whitespace or control characters. They must be unique within each direction;
inputs and outputs may share names. Port names and transformer names allow
120 characters; descriptions allow 2000.

Responses add generated ID/timestamps and a `fields` snapshot to every port.
Dynamic variable snapshots are empty. List types are resolved from saved Fields
under row locks in sorted UUID order. Fields definitions referenced on either
side cannot be deleted; snapshotted keys/types cannot be removed or changed
until the dependent ports release them. New Fields keys may be added, and
saving the transformer refreshes its snapshots. Switching a port to a dynamic
variable releases its Fields reference. Port replacement, including name swaps,
occurs atomically in one transaction.

Tests cover mixed ports, variable-only definitions, both-sided Fields protection,
kind switching, persistence, ordering, validation, CRUD, and deletion cleanup.

Migration V11 adds `directory` (up to 2048 characters) and `wasm_file_name`
(up to 255 characters) to Transformers. New/edited configurations require both.
Filename validation matches Mapper: a `.wasm` extension, no directory separators,
and no control characters. Both components are preserved exactly; spaces in
file/directory names are allowed. Existing transformer rows receive empty values
and remain visible; configure their WASM location when editing them. File
existence checks and module execution remain unimplemented.

## Saved-item timestamps and search

Fields, Tables, Normalize rules, Conditional rules, Mappers, and Transformers
already persist and return `createdAt` and `updatedAt`. Migration V12 adds
nullable `created_at` to `etl_connections`; Connector list responses now also
return both timestamps. New connector saves assign creation/update instants,
and updates preserve creation time while advancing update time. Legacy
connectors retain null creation times, including after editing, because the
original creation time cannot be recovered from the old update timestamp.
Migration and API tests cover this behavior. Password handling is unchanged.

The frontend provides search, relevant type filters, local creation-date ranges,
and sorting over each existing list endpoint’s results. No server-side search or
pagination parameters are introduced. Only documented public fields are searched;
connections have no description field, so their search targets name, connector
type, host/database/username, file directories, filters, and charset. Dates display in the browser’s timezone.

## File connectors

`type: "file"` uses the existing `/api/connections` CRUD and test endpoints. No
new migration is needed: settings remain a map of strings. The module declares
`camel-file` 4.22.0 explicitly. Settings follow the [Apache Camel 4.22 File
component](https://camel.apache.org/components/4.22.x/file-component.html).
This is a File **consumer** configuration; workflow execution is not started by
saving or testing the connector.

```json
{
  "name": "CDR inbox",
  "type": "file",
  "settings": {
    "directoryName": "/data/inbox",
    "move": ".processed",
    "moveFailed": ".invalid",
    "includeExt": "csv,txt",
    "recursive": "false",
    "autoCreate": "true",
    "readLock": "changed",
    "readLockTimeout": "10000",
    "readLockCheckInterval": "1000",
    "delay": "500",
    "initialDelay": "1000"
  }
}
```

Supported settings:

| Key | Purpose / default |
| --- | --- |
| `directoryName` | Required literal source directory on the Java service host; no dynamic expressions or property placeholders. |
| `move` | Destination directory or Camel File expression after successful processing; application default `.processed`. |
| `moveFailed` | Destination directory or Camel expression after failed processing; application default `.invalid`. |
| `preMove` | Optional in-progress move directory/expression. |
| `fileName` | Optional exact filename or Camel File expression filter. |
| `include`, `exclude` | Optional case-insensitive Java filename regexes, supplied as plain patterns. |
| `includeExt`, `excludeExt` | Optional comma-separated extensions. |
| `charset` | Optional supported JVM charset; blank leaves Camel's encoding default. |
| `recursive` | Poll subdirectories; default false. |
| `autoCreate` | Create a missing source during execution; default true. |
| `delay`, `initialDelay` | Milliseconds; defaults 500 and 1000. Delay must be positive and initial delay non-negative. |
| `maxMessagesPerPoll` | Non-negative integer; application default 0 (unlimited). |
| `readLock` | `none` (Camel default), `markerFile`, `changed`, `fileLock`, `rename`, `idempotent`, `idempotent-changed`, or `idempotent-rename`. |
| `readLockTimeout`, `readLockCheckInterval` | Milliseconds; defaults 10000 and 1000. Timeout 0 means indefinite; positive timeout must exceed the interval for timed strategies. |
| `readLockMinAge`, `readLockMinLength` | Milliseconds / bytes for changed-based locks; defaults 0 / 1. |

Unrecognized keys, invalid booleans/numbers/regexes/charsets, and invalid lock
settings return HTTP 400. Path and expression strings are preserved without
trimming. All strings are limited to 2048 characters to match settings storage.
The UI and serializer keep File settings separate from PostgreSQL settings and
credentials. Connector type is immutable after creation, protecting existing
references from being switched to an incompatible type.

Relative move directories resolve from the consumed file's parent. Expressions
may compute a destination filename. `moveFailed` means failed exchanges, not an
automatic content-validation rule: future workflow validation must mark the
exchange failed to use this destination. This form supports a curated subset of
File consumer options; it does not expose every Camel option or producer options.

**Test directories** checks source and literal move destinations (or their nearest
existing parents) for directory/read/write/search access. If the source is missing
with `autoCreate=true`, the test checks its existing ancestor and reports that it
can be created later; it does not create it. With autoCreate disabled, a missing
source fails the test. Destination expressions are explicitly reported as requiring
execution-time checks. Tests do not start consumers, evaluate destination
expressions, create folders, or move/read/delete source files. These access checks
cannot guarantee that permissions remain unchanged when a workflow eventually runs.

## Advanced PostgreSQL connector properties

The PostgreSQL connector accepts `currentSchema`, `connectTimeout`,
`socketTimeout`, and `sslrootcert` in its saved settings map, matching pgJDBC
property names. The UI exposes them under Advanced PostgreSQL settings. All
operations using `PostgresConnectionFactory` (connection testing, optional
database creation, and target table/schema operations) receive these configured
properties instead of fixed timeouts.

| Setting | Meaning | Application default |
| --- | --- | --- |
| `currentSchema` | Optional default schema/search path; accepts a comma-separated schema list. | Driver/database user default when omitted or blank. |
| `connectTimeout` | Socket connection timeout in seconds. | 5 seconds, preserving prior application behavior. |
| `socketTimeout` | Socket read timeout in seconds. | 10 seconds, preserving prior application behavior. |
| `sslrootcert` | Optional root CA certificate path on the Java service host, used for SSL verification. | pgJDBC's certificate location when omitted or blank. |

Timeouts accept whole numbers from 0 through 2147484; 0 disables that timeout.
Omitted or blank timeouts receive the application defaults. Optional schema and
certificate values allow up to 2048 characters, reject null characters, and are
preserved exactly, including quoted schema identifiers or spaces in certificate
paths. Blank values are omitted from JDBC properties so driver defaults apply.
Existing saved connectors without the new keys remain compatible, without a
migration. Password preservation and response redaction are unchanged.

Example additional settings:

```json
{
  "currentSchema": "analytics,public",
  "connectTimeout": "30",
  "socketTimeout": "120",
  "sslrootcert": "/opt/etl/certs/root.crt"
}
```

Use a verification SSL mode, such as `verify-full`, when configuring a custom CA
for certificate validation. Query, polling, parameter, result, and transaction
options still belong to future Camel workflow steps. Adding these connection
properties does not start a Camel SQL consumer or register a Camel DataSource.
See the [pgJDBC connection-property reference](https://jdbc.postgresql.org/documentation/use/).

Tests verify validation boundaries, persistence/API round trips, legacy defaults,
and the exact properties passed to `DriverManager`, including custom schemas,
certificate paths, configurable timeouts, and disabled timeouts.
