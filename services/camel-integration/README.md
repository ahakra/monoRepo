# Configuration

Start PostgreSQL from the repository root:

```sh
docker compose --env-file .env -f docker/compose.postgres.yml up -d
```

Create `.env` from `.env.example` first if needed (`cp .env.example .env` from the repository root). Compose requires nonempty `POSTGRES_DB`, `POSTGRES_USER`, and `POSTGRES_PASSWORD`. Camel reads the same root `.env` when launched from the repository root or this service directory; environment variables can override those values. The default JDBC URL uses `localhost:5432` and `POSTGRES_DB`. Set `POSTGRES_JDBC_URL` for another database host or port.

If Java fails while initializing Flyway, check `docker compose --env-file .env -f docker/compose.postgres.yml ps` and container logs from the repository root. A restarting container with “superuser password is not specified” means Compose was started without the settings. Rerun the command above with `--env-file .env`; the existing data volume is preserved. If port 8081 is occupied, check whether an IDE instance is already serving the API before starting a second instance.

Run `./mvnw spring-boot:run` in this directory, and `npm run dev` in `apps/workflow-designer`. Open **Connectors** in the sidebar. The Vite development server proxies `/api` to Camel on port 8081. Production hosting must also proxy `/api` to Camel.

Flyway creates `etl_connections` and `etl_connection_settings`; JPA maps these tables and validates their schema. Existing `integration_connections` rows are migrated once; the legacy table is retained as a backup. Saved configurations survive restarts through the existing Docker volume. The target connection host is resolved from the Camel process: use `localhost` when running Camel on the host, or `postgres` on the same Docker network.

API:

- `GET /api/connections`: list configurations, excluding passwords.
- `POST /api/connections`: create a configuration.
- `PUT /api/connections/{id}`: update; blank or omitted password preserves the saved password.
- `DELETE /api/connections/{id}`: delete a configuration.
- `POST /api/connections/test`: test unsaved fields.
- `POST /api/connections/{id}/test`: test edited fields, reusing the saved password when blank.

Create, update, and test accept `name`, `type`, `password`, and a type-specific `settings` map. For example:

```json
{
  "name": "Analytics destination",
  "type": "postgres",
  "password": "your-password",
  "settings": {
    "host": "localhost",
    "port": "5432",
    "database": "analytics",
    "username": "camel_etl",
    "sslMode": "disable",
    "createDatabaseIfNotExists": "true"
  }
}
```

Settings values are strings. PostgreSQL supports SSL modes `disable`, `require`, and `verify-full`. Saving only persists configuration. With `createDatabaseIfNotExists` enabled, **Create & test** first tries the target database. Only a missing-database error triggers creation through the `postgres` maintenance database, followed by another connection test. Existing databases do not require creation privileges. The account must have `CREATEDB` to create a missing database; creation runs outside a transaction as required by [PostgreSQL](https://www.postgresql.org/docs/current/sql-createdatabase.html). Turning the option off never creates a database. Configurations are not yet attached to pipeline execution.

The Java packages separate responsibilities:

- `api`: HTTP controller, request/response DTOs, error mapping.
- `application`: framework-independent connection use cases and commands.
- `domain`: connection model, persistence port, and connection type handler contract.
- `infrastructure/persistence`: JPA entity, Spring Data repository, and persistence adapter.
- `infrastructure/postgres`: PostgreSQL validation, JDBC connection factory, and connection testing/creation.

To add another type, register a `ConnectionTypeHandler` bean with its own settings validation and testing behavior, and add its frontend form. The application service dispatches by type; the entity and repository have no database-specific fields. MySQL and HTTP are extension points, not implemented types.

## Fields

Open **Schemas & Tables → Fields** to create, edit, or delete named, reusable field dictionaries. Each definition includes the default entries `id: uuid` and `datetime: datetime`; their keys and types are fixed. Add custom entries such as `name: string` and `lastname: string`.

The field dictionary describes future data columns. Separately, each saved definition has its own UUID `id`, `createdAt`, and `updatedAt` metadata, generated by the service. Saving a definition creates no external table and needs no connection.

- `GET /api/fields`: list saved definitions, most recently updated first.
- `POST /api/fields`: create a definition; returns the saved definition with HTTP 201.
- `PUT /api/fields/{id}`: replace the name and dictionary; returns the saved definition, preserving its ID and creation time.
- `DELETE /api/fields/{id}`: delete a definition and its entries; returns HTTP 204.

Create and update accept:

```json
{
  "name": "Customer",
  "fields": {
    "id": "uuid",
    "datetime": "datetime",
    "name": "string",
    "lastname": "string"
  }
}
```

Default entries are added when omitted, and conflicting types are rejected. Supported types are `string`, `integer`, `long`, `decimal`, `boolean`, `date`, `datetime`, `uuid`, and `json`. Keys must match `[a-z_][a-z0-9_]{0,62}`. Names contain 1–120 characters; definitions contain at most 100 entries including defaults. The editor rejects duplicate keys before saving. Invalid definitions return HTTP 400 with a problem detail; missing definitions return HTTP 404.

Flyway migration V3 adds `etl_field_definitions` and `etl_field_entries` to internal platform persistence. The `fields` Java package follows the same API/application/domain/infrastructure separation as connections. Migration V4 seeds **CDR (Call Detail Record)** once, with `id`, `datetime`, `call_id`, `caller_number`, `called_number`, `start_time`, `end_time`, `duration_seconds`, `direction`, `call_status`, `charge_amount`, and `currency`. This sample contains only field definitions, not call records. It can be edited or deleted like other definitions, and deleting it does not cause it to be reseeded on restart.

## Tables

Open **Schemas & Tables → Tables**, choose an existing PostgreSQL connection and one Fields definition, and provide a configuration name, existing schema (default `public`), and table name. **Add all fields** selects the entire dictionary; **Add one field** adds only the chosen key. Fields can be removed from the selection, including `id` and `datetime`. At least one field is required. Keys and types cannot be entered independently of the selected dictionary. Changing the Fields definition clears the selection.

Saving stores configuration only. From the saved list, inspect **View CREATE TABLE SQL**, then use **Create PostgreSQL table** to review the target and execute creation. This uses the saved connection credentials without returning them to the browser. It does not create a database or schema. An existing target relation returns a conflict rather than being modified. Editing or deleting a saved configuration never alters or drops an external table, and a successful creation message does not track future changes to that table.

- `GET /api/tables`: list configurations, including selected `columns` as a key/type dictionary and generated `sql`.
- `POST /api/tables`: save a configuration; returns the saved configuration with HTTP 201.
- `PUT /api/tables/{id}`: replace a configuration; returns the saved configuration.
- `DELETE /api/tables/{id}`: remove configuration only, with HTTP 204.
- `POST /api/tables/{id}/create`: explicitly create the physical PostgreSQL table; returns a success message.
- `GET /api/tables/{id}/schema-plan`: compare the current PostgreSQL columns with the saved mapping; returns a review fingerprint and proposed changes.
- `POST /api/tables/{id}/schema-changes`: apply selected changes from a current review.

Create and update accept:

```json
{
  "name": "CDR destination",
  "connectionId": "<saved-postgres-connection-uuid>",
  "fieldDefinitionId": "cd000000-0000-4000-8000-000000000001",
  "schemaName": "public",
  "tableName": "cdr_records",
  "fields": ["id", "datetime", "caller_number", "called_number", "duration_seconds"]
}
```

The API independently enforces PostgreSQL connection type, validates selected keys against the saved definition, rejects duplicate or empty selections, and derives column types on the server. It rechecks the connection and selected fields before external creation. Schema, table, and column identifiers follow the same lowercase 63-character rules as field keys, and generated SQL quotes each identifier. Types map as follows:

| Field type | PostgreSQL type |
| --- | --- |
| `string` | `TEXT` |
| `integer` | `INTEGER` |
| `long` | `BIGINT` |
| `decimal` | `NUMERIC` |
| `boolean` | `BOOLEAN` |
| `date` | `DATE` |
| `datetime` | `TIMESTAMP WITH TIME ZONE` |
| `uuid` | `UUID` |
| `json` | `JSONB` |

Columns are nullable, with no automatic primary keys, defaults, or indexes. Creation executes a single constrained `CREATE TABLE` statement. A timeout may leave creation outcome uncertain; check the target database before retrying.

Migration V5 adds `etl_table_definitions` and `etl_table_columns`, with a unique target per saved connection/schema/table. Foreign keys prevent deleting a referenced connection or Fields definition (HTTP 409). The Fields service prevents removing, renaming, or changing the type of a selected field until **every** dependent table configuration releases it. These conflicts return HTTP 409. Field definitions returned by the API include `usedBy` references with table IDs, names, and selected keys/types. The editor locks used keys and types, shows their references, and disables deletion of used definitions. Unselected fields and definition names can still change. Field updates, deletes, and table-mapping saves hold the same definition row lock across usage validation and persistence, preventing concurrent mapping saves from bypassing the check. Table configuration stores a snapshot of selected keys and types.

### Reviewing and applying column changes

To change a field type or key:

1. Remove the column from every affected table mapping and save those mappings.
2. Edit the field in Fields and save.
3. Add the updated field back to the table mapping and save.
4. Use **Review column changes**, select the desired changes, review their SQL, acknowledge any DROP/ALTER data-loss risk, and apply.

To drop a physical column, remove it from the mapping, save, then select the proposed DROP in the review. Saving a mapping alone does not execute column changes. The review also lists actual database columns absent from the mapping, including columns added outside the application; all changes start unselected. Renaming a field produces separate ADD and DROP suggestions and does not copy existing data to the new name.

ADD creates a nullable column using the allowlisted field type. ALTER converts values using an explicit cast to that type, which can lose precision or fail for incompatible data or defaults. DROP permanently removes column values. The service never appends CASCADE. Partitioned/inherited tables and type changes to identity/generated columns require direct PostgreSQL management.

Example apply request:

```json
{
  "fingerprint": "<fingerprint-returned-by-schema-plan>",
  "changeIds": ["alter:duration_seconds", "drop:obsolete_column"],
  "acknowledgeDataLoss": true
}
```

The client submits change IDs, never executable SQL. The server locks the saved mapping and the target PostgreSQL table, reads current column metadata and constraints, rebuilds the plan, and rejects a stale fingerprint or unknown change ID. Only selected changes execute, in one PostgreSQL transaction with lock and statement timeouts. Conversion or dependency failures roll back that transaction. After connection loss near commit, inspect the database and refresh the plan before retrying; the UI requires a fresh review after an apply error. PostgreSQL permissions still determine which operations the saved connection can execute.

Migration and CRUD tests use H2; PostgreSQL JDBC creation, schema planning, selected execution, acknowledgment, stale-plan rejection, and rollback/error handling are tested with mocked connections.

This first iteration is for a trusted local workspace: the API has no authentication and passwords are stored as plaintext in the configuration database, although never returned by the API. Restrict access to the service and database. Add authentication and a secrets store before exposing it to other users.

Run `./mvnw test` for service tests (isolated H2 test database) and `npm run build` / `npm run lint` in the frontend directory.


Formatting is configured at the repository root. Run `npm ci` there once, then `npm run format` to format the Java and frontend sources, or `npm run format:check` to check them. Java uses four-space indentation; JavaScript, JSX, and CSS use two spaces.

## Normalize rules

Migration V6 adds `etl_normalize_rules`. Use the Rules page to configure a name,
optional description, Fields definition, source key, condition/value,
action/value, and destination key. Both keys must belong to the selected
Fields definition and have `string` or `text` type. The current Fields API
exposes `string` as its text type. The service validates selectors and values
independently of the UI, and locks the Fields definition while saving a rule.
Referenced definitions cannot be deleted; referenced keys cannot be removed
or changed to non-text types until the rule is edited or deleted.

Endpoints:

- `GET /api/rules/normalize`: list saved rules (`id`, `spec`, `createdAt`, `updatedAt`).
- `POST /api/rules/normalize`: save a new rule from a spec.
- `PUT /api/rules/normalize/{id}`: update a saved rule from a spec.
- `DELETE /api/rules/normalize/{id}`: delete a saved rule.
- `POST /api/rules/normalize/test`: evaluate an unsaved spec with `{ "spec": {...}, "record": {...} }`.
- `POST /api/rules/normalize/{id}/apply`: evaluate a saved rule against a JSON record supplied directly as the request body.

Example spec:

```json
{
  "name": "Local phone number",
  "description": "Remove the country prefix when present",
  "fieldDefinitionId": "<saved-fields-uuid>",
  "sourceField": "phone",
  "condition": "STARTS_WITH",
  "conditionValue": "+961",
  "action": "REMOVE_PREFIX",
  "actionValue": "+961",
  "destinationField": "normalized_phone"
}
```

Conditions: `STARTS_WITH`, `ENDS_WITH`, `CONTAINS`, `EQUALS`, `LENGTH_EQUALS`,
`LENGTH_GREATER_THAN`, `LENGTH_LESS_THAN`. Length values are strings containing
non-negative integers up to 2147483647; length counts Unicode code points.
Text comparisons are case sensitive. `EQUALS` accepts an empty string.

Actions: `COPY`, `ADD_PREFIX`, `ADD_SUFFIX`, `REMOVE_PREFIX`, `REMOVE_SUFFIX`,
`TRIM`, `UPPERCASE`, `LOWERCASE`, `REPLACE`. Prefix/suffix actions require a nonempty
`actionValue`, preserved exactly (including whitespace). Removal affects only
a matching prefix/suffix once. Case conversion uses `Locale.ROOT`; trim uses
Java `String.strip()`. For `REPLACE`, `actionValue` is the required nonempty find text and `replacementValue` is the replacement string (up to 2000 characters). Replacement is literal and case sensitive, affects every occurrence, and allows an empty replacement to remove text. No regular expressions or replacement escape syntax are used. Migration V7 adds `replacement_value` with an empty default for existing rules. Other actions ignore `replacementValue`; actions without a text argument ignore `actionValue`.

Evaluation returns `{ "matched": true|false, "record": {...} }`. On a match,
the transformed source replaces the destination (which may be the source
itself). On a non-match the record is unchanged, including an existing
destination value. Null, absent, or non-string sources never match. The Java
evaluator copies its input and preserves unrelated fields and null values.
The UI's sample test calls this same Java evaluator. Rules are not yet attached
to the workflow designer or automatic Camel execution.
